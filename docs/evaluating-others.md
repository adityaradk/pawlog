# Evaluating Other Teams – Nielsen’s 10 Heuristics Checklist

Use this while evaluating another team’s prototype. Think aloud, try their tasks without help, and write down every problem with a heuristic and a severity (0 = not a problem … 4 = catastrophe).

| # | Heuristic | Ask yourself |
|---|---|---|
| H1 | Visibility of system status | After I act, can I tell right away whether it worked and what changed? |
| H2 | Match between system and the real world | Does it use words and concepts the target user already knows, not developer jargon? |
| H3 | User control and freedom | Can I undo, cancel, or go back easily if I make a mistake? |
| H4 | Consistency and standards | Do similar things look and behave the same way across screens (and like other apps)? |
| H5 | Error prevention | Does the design stop me from making mistakes in the first place (constraints, confirmations, defaults)? |
| H6 | Recognition rather than recall | Are options and past information visible, or do I have to remember them? |
| H7 | Flexibility and efficiency of use | Are there shortcuts for frequent actions without confusing new users? |
| H8 | Aesthetic and minimalist design | Is every element on the screen useful, or is there clutter competing for attention? |
| H9 | Help users recognize, diagnose, and recover from errors | Do error messages say what went wrong in plain language and how to fix it? |
| H10 | Help and documentation | If I get stuck, is help available where I need it? |
